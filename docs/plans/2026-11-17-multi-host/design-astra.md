# Agent Kaizen on Codex and Copilot

Independent design · 2026-11-17 · repository baseline `d8a4cb7`, plugin 0.11.0.

**Ship three local install targets from one source tree.** A user should be able to install Kaizen, explicitly invoke scan, start a project ledger, review a measurement, and undo an applied change without installing Claude Code. Codex CLI and its local IDE integration are one candidate package with two acceptance runs. Copilot CLI and the built-in VS Code chat agent need separate hook contracts. GitHub's cloud coding agent is a reasonable consumer of repository instructions and selected skills. A personal, recurring, cross-session audit service there is outside this release.

**Evidence boundary.** I checked versioned OpenAI, GitHub and Microsoft distributions locally on 2026-11-17, including shipped documentation, command help, schemas and release notes. A curl request using the owner's browser User-Agent failed at DNS resolution. The Sources section distinguishes the artifacts checked from current upstream pages still to verify. The host versions below identify evidence, not minimum supported versions. The first packet settles the moving contracts before public compatibility claims.

## Host contracts and install routes

### OpenAI Codex CLI and local Codex IDE

- **Distribution.** Codex 0.167.0 exposes `codex plugin marketplace add <local-path|owner/repo[@ref]|git-url>`, `codex plugin add NAME@MARKET`, `codex plugin list` and `codex plugin remove NAME@MARKET`. The official marketplace uses `.agents/plugins/marketplace.json` with `source: {source: "local", path: "./plugins/agent-kaizen"}`. The native plugin manifest is `.codex-plugin/plugin.json` and can point to `./skills/` and a hook JSON file. The binary also recognizes a Claude manifest path. Native defaults can *add* discovered components to explicit declarations. An isolated package prevents accidental registration of the root Claude hooks. [Codex plugin authoring](https://developers.openai.com/codex/plugins/build/)
- **Discovery and invocation.** Plugin skills and standalone `.agents/skills/<name>/SKILL.md` are separate routes. The installed runtime references project/user agent skills and the Codex-home skills directory (default `~/.codex/skills`). Emit name and description. Set `policy.allow_implicit_invocation: false` in each skill's `agents/openai.yaml`. OpenAI's shipped reference documents explicit invocation with `$skill`. Verify the installed, namespaced spelling through the picker. Drop unneeded Claude frontmatter from the generated view. Runtime evidence does not establish that the Claude disable flag alone enforces the same policy. Use AGENTS.md, nested guidance and AGENTS.override.md according to Codex precedence. Plugin commands and slash menus are optional discoverability aids. [Skills](https://developers.openai.com/codex/skills/) · [AGENTS.md](https://developers.openai.com/codex/guides/agents-md/)
- **Agents.** A standalone custom role uses a TOML definition in project `.codex/agents/` or the Codex-home agent directory, with name, description and `developer_instructions`. Model and reasoning options are optional. A profile selects configuration and does not register an auditor. OpenAI's catalog also has plugin-level Markdown agents. Check the plugin role loader and effective tool restrictions before choosing the native export. Prefer a read-only role. A fallback explicit audit skill reads a precomputed report if the host cannot constrain a shell. [Subagents](https://developers.openai.com/codex/subagents/)
- **Hooks.** The shipped catalog has root `hooks.json` examples with a top-level `hooks` map, PascalCase events, matcher groups and command handlers. The Codex-home `config.toml` and a trusted project’s `.codex/config.toml` participate in configuration layering. Check standalone hook-file discovery and precedence on the selected version. Use the plugin-owned hook file. The runtime contains SessionStart, SessionEnd, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact, SubagentStart/Stop and Stop. Its wire types include `session_id`, `agent_id`, `agent_type`, `hook_event_name`, `tool_name`, `tool_input`, `tool_use_id` and `tool_response`. Supported event outputs include `hookSpecificOutput.additionalContext` and a pre-tool permission decision/reason. Field optionality, tool aliases, failure coverage, async operation and trust acceptance need event-specific captures. The binary includes `PLUGIN_ROOT` and `CLAUDE_PLUGIN_ROOT` for plugin integration. Check their values in the hook process. Never assume an interactive shell inherits them. [Hook configuration](https://developers.openai.com/codex/config-advanced/#hooks)
- **History and IDE.** Legacy rollout JSONL supports the existing reader. The official CLI now offers `migrate-rollouts` to move legacy sessions to **paginated thread history**. An empty legacy directory, archived sessions, ephemeral mode or a remote execution home can all leave the reader with incomplete coverage. Do not migrate sessions, scrape internal databases or count the CLI prompt-history file as usage. Test the local IDE extension with its actual backend, home, profile and workspace. A plugin list in the terminal alone proves nothing about the IDE's enabled features or data store. [CLI release](https://github.com/openai/codex/releases/tag/rust-v0.167.0) · [IDE](https://developers.openai.com/codex/ide/)

### GitHub Copilot CLI

- **Distribution.** The official `@github/copilot` 1.0.73 runtime bundled with VS Code documents `/plugin marketplace add <source>`, `/plugin install <name>@<market>`, direct `owner/repo[:path/to/plugin]` installs, update and uninstall. Its marketplace help includes local directories. Loader evidence includes root `plugin.json`, `.plugin/`, `.github/plugin/` and `.claude-plugin/` forms. Use an isolated native package plus `.github/plugin/marketplace.json` for the portable distribution. Directly installing this repository's current Claude marketplace could load handlers before adaptation. [CLI repository and changelog](https://github.com/github/copilot-cli) · [CLI guide](https://docs.github.com/copilot/how-tos/use-copilot-agents/use-copilot-cli)
- **Discovery and instructions.** CLI help lists repo `.github/skills/`, `.agents/skills/`, `.claude/skills/`, personal `~/.copilot/skills/`, `~/.agents/skills/` and directories registered by `/skills add`. `/skills list`, `/skills info <name>` and reload allow diagnosis. GitHub's bundled skill-authoring text uses name, description, `user-invocable` and `disable-model-invocation`. Check actual loader enforcement separately from agent frontmatter support. Register only the plugin route by default. Use explicit invocation from the installed command/skills UI. If the CLI indexes a disabled skill implicitly, ship a user-only plugin command that reads a private workflow file outside discovery. Use repository `.github/copilot-instructions.md` or applicable `AGENTS.md`, with additional personal and scoped instruction locations. The bundled runtime also recognizes `CLAUDE.md`. A repository can therefore already supply relevant guidance before the install. Reuse the owner's existing applicable file. [GitHub Copilot customization](https://docs.github.com/en/copilot/customizing-copilot)
- **Agents.** Use `agents/kaizen-auditor.agent.md` in the bundle, or `.github/agents/*.agent.md` in an explicitly requested repository install. Check the effective personal agents directory (normally `~/.copilot/agents/`) under custom CLI configuration. CLI supports description, name, tools and model selection. Its custom-agent parser handles `disable-model-invocation` and `user-invocable`. The agent picker provides a manual route. Only enable delegation and shell use where verified. Omit hardcoded model aliases, tool IDs belonging to Claude and `omitClaudeMd`. [GitHub custom agents](https://docs.github.com/en/copilot/reference/custom-agents-configuration)
- **Hooks.** Native repository files are `.github/hooks/*.json`. The native schema uses version 1, a `hooks` object with arrays of commands, lower-camel event names, `type: command`, shell-specific `bash`/`powershell`, optional `cwd`, `env` and `timeoutSec`. The bundled runtime includes sessionStart/End, userPromptSubmitted, preToolUse, postToolUse, postToolUseFailure, errorOccurred, agentStop, subagentStart/Stop and preCompact. The command receives event-specific JSON on stdin. Common/native fields include timestamp and cwd, and in applicable events sessionId, prompt, toolName, toolArgs and toolResult. Handle a JSON-encoded arguments string only where the actual event schema calls for it. Native pre-tool denial uses stdout JSON with top-level `permissionDecision` and `permissionDecisionReason`. Additional context is event-specific. A printed notice is useful only after demonstrating that the target session receives it. Root aliases in the runtime include `COPILOT_PLUGIN_ROOT`, `PLUGIN_ROOT` and `CLAUDE_PLUGIN_ROOT`. Test the command environment and effective directory. [GitHub hook reference](https://docs.github.com/en/copilot/reference/hooks-configuration)
- **History.** The bundled runtime resolves its configuration directory and `COPILOT_HOME` before the default home. Local files normally include `session-state/<id>/events.jsonl` and `workspace.yaml`. Session events use `type` and `data` with session/turn/tool lifecycle records. SDK handling of live `assistant.usage`, `session.usage_checkpoint` and shutdown model metrics does not prove each event persists. Treat shutdown aggregates as cumulative. Identify which persisted fields give per-window, per-project coverage before offering token totals. Prefer explicit, project-scoped use over broad session discovery. [Vendor package](https://www.npmjs.com/package/@github/copilot/v/1.0.73)

### GitHub Copilot coding agent in the cloud

A GitHub-managed job works on a repository and exposes session logs through GitHub. Repository instructions, selected agent skills, custom agent profiles and repository hooks make individual project workflows plausible. A desktop CLI marketplace installation, persistent user home, local transcript tree and OS scheduler do not travel with the job. Interactive slash invocation and the opportunity to confirm a personal settings change are different there. Treat cloud as **outside the supported install matrix**. Portable project guidance and explicit repo-level measurements remain useful. Do not install personal hooks, request additional Actions permissions, import transcripts, or arrange a network path to a developer's machine. Exact cloud hook events/outputs, supported frontmatter and log export remain upstream checks, not prerequisites for the local release. [Coding agent overview](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent) · [Coding agent in VS Code](https://code.visualstudio.com/docs/copilot/copilot-coding-agent)

## Architecture and boundaries

1. **Author once, build self-contained packages.** Keep the original Claude layout as the canonical input, including each skill and the auditor's long-form procedure. Add a Python 3.9 stdlib exporter, proposed `tools/package-host`, small host templates in `hosts/{codex,copilot-cli,vscode}/` and a shared inventory in `hosts/components.json`. From a checkout or CI, build versioned directories under an explicit output root. Each marketplace contains `plugins/agent-kaizen/` with its manifest, explicit entries, runtime docs, scripts, script data, templates and license. VS Code can consume the plugin directory directly. Release ZIPs contain real files and executable metadata. No symlink outside a package, home-relative resource reference, Git checkout, build step or new runtime service is required of a release user.
   Shared SKILL.md discovery alone would leave Claude slash calls, writes into the Claude home and hook responses in the wrong protocol. Keeping three hand-edited procedure trees would require four copies of every future workflow fix. Generate the repeated views and hand-maintain only the small, behavior-specific differences.
2. **Adapt meaning as well as paths.** Keep shared procedures in source. Convert known Claude-specific paragraphs to named host substitutions, covered by inventory checks. For divergent workflows, such as guardrails and scheduling, use a short host-specific procedure. Fail export on unclassified host-specific references. Generate native skill metadata, invocation spelling and in-package relative references. All relative links resolve from the defining file. Shell examples resolve the installed helper from the loaded skill's file location, quote its absolute path and pass the actual workspace separately. A hook root variable is available only where its host supplies it. The host's documented plugin entry point can provide a trusted root for a hook. Never search the working directory for a similarly named executable. Package runtime references including `docs/autonomy.md`, `docs/outcome-log.md`, `docs/flow.md`, `pricing.json`, preambles and prompts. Test a relocated extracted package without the checkout.
3. **Separate Kaizen state from host input.** Add an explicit `KAIZEN_HOME` for portable entry points, with documented platform user-state defaults (XDG on Unix, Application Support on macOS, LocalAppData on Windows). New-host entry points supply this context to their child processes. Existing Claude entry points retain current resolution, environment overrides, defaults and ledger behavior. A Claude transcript root is still resolved from `CLAUDE_CONFIG_DIR`, a Codex root from `CODEX_HOME`, a Copilot root from the runtime's config choice or an explicit path. Never redirect `CLAUDE_CONFIG_DIR` just to relocate output. Existing overrides such as `AUDIT_DIR` where honored, `KAIZEN_BACKUP_DIR` and `KAIZEN_USAGE_DB` keep precedence. Select host and workspace explicitly rather than by installed executable or account. No automatic migration. Users can explicitly share existing Kaizen state. Project config, ledger and recorded evidence keep their current formats.
4. **One hook implementation per behavior.** Add one small stdlib dispatcher at the host boundary. Its inputs are the selected host, registered event and bounded JSON on stdin. Map only observed tool IDs and typed arguments to the existing shell handler's contract. Pass the working directory as a value, keep user fields out of command strings, invoke a fixed argv, and translate only the supported return fields. Scope session-counter identities by host, role and session. Preserve backups, existing overrides, project enrollment, main-agent and interruption filters, lock deadlines, hook ordering and quiet failures. Only a positive policy match on a supported operation can deny it. Keep unsupported event/decision pairs unregistered. No fake PostCompact on start and no shell-command parsing to approximate a Read. First ship the notice and deterministic checks that actually work. Offer the optional guards individually with a preview. A missing approved interpreter, Bash or jq yields explicit feature status at setup. Avoid installing dependencies from hooks.
5. **Portable auditing has an explicit source.** Keep the existing default report schema and hot path for legacy callers. A portable wrapper requests the selected host and exact project. Return source, measured scope, coverage (complete/partial/unavailable) and missing-data reason. Preserve `--no-write` everywhere. Add a CLI JSONL reader only when a sanitized real shape demonstrates attributable, persisted usage. Deduplicate event/session IDs across resume, respect a baseline before the window, and distinguish deltas from terminal snapshots. If only a whole-session aggregate exists, count it only when the entire attributable session is in-window, label the limitation and skip overlapping sessions. Do not add a shutdown total to per-turn usage. Report Copilot credits, premium requests and token counts separately if available. Never infer dollars from a subscription or price unknown models. Without usage, show measured session/activity counts separately, reference a supplied report, or offer the synthetic demo. No prompt bodies, true paths, raw transcripts, secrets or private audit output in fixtures or release evidence.
6. **Keep changes reversible.** The native plugin manager owns plugin installation. No generated bundle writes settings on activation. Opt-in integrations target a chosen file/profile and preserve unknown settings, existing hooks and instructions. Show a diff, make a Kaizen backup with the target's prior state, and identify precisely the owned artifact. Reapplying a template or installing twice must not duplicate an entry. Roll back a partial update and leave user-modified or foreign files in place on uninstall. Use the existing linker's ownership checks where applicable. A new install may read the project config. It must not silently inherit a writable global allowlist, expand scheduled authority, or run another vendor's authenticated CLI. Respect the existing `propose`, `safe`, `auto` and hard-stop rules, with host-specific supported targets. For the new hosts, keep model-backed scheduling and managed machine-level changes proposal-only until independently supported.

## Distribution, release and operations

- **Package layout.** `tools/package-host --host HOST --out PATH` is a proposed build-time interface. Supported host IDs are `codex`, `copilot-cli` and `vscode`. Under PATH, the first two builds produce distinct marketplace roots and plugin folders. The third produces a local plugin directory. Only generated target packages contain generated skill views. Runtime source and package templates stay reviewable in Git. Build from an explicit allowlist. Never package the checkout wholesale, `.git`, plans, user config, audit output or private data. Keep the final ZIP and extracted layout equivalent on Windows and POSIX. Keep a stable installation directory across upgrades, separate from state.
- **Install docs.** From a release, extract the matching artifact to a directory of the user's choice. For Codex, run `codex plugin marketplace add "<extracted-marketplace>"`, then `codex plugin add agent-kaizen@agent-kaizen-tools`; open a new local CLI or IDE session and locate the explicit scan skill. For Copilot CLI, enter `/plugin marketplace add <extracted-marketplace>`, then `/plugin install agent-kaizen@agent-kaizen-tools`; verify via the plugin and skills lists. For VS Code, add the absolute extracted plugin directory as a true-valued entry in the active profile's `chat.pluginLocations` using Settings, open trusted local agent chat, and invoke the scan command from the picker. Supply an **Install Plugin from Source** example only for an actually published supported source. Document host switches, workspace profiles, quoting and remote execution. GitHub direct-install syntax works only for a Git ref actually containing an assembled package. Retain the existing Claude README commands.
- **Upgrade and rollback.** Record the artifact version and the selected installation path, keep one previous artifact, and exercise an upgrade with an existing ledger. Use native remove/disable, replace the package, re-register or refresh the marketplace as required, then verify scan. For uninstall use `codex plugin remove agent-kaizen@agent-kaizen-tools`, Copilot's `/plugin uninstall agent-kaizen@agent-kaizen-tools`, or remove the single VS Code plugin location. Remove a marketplace entry only if Kaizen owns it. Review and optionally undo separately installed hook snippets and jobs. Preserve reports, user configuration, ledgers and backups unless the owner separately requests their removal. Document how to select the previous artifact.
- **Versioning.** Source version remains `.claude-plugin/plugin.json`. Every generated manifest uses that value. Extend the runtime-change path list to `hosts/**`, `tools/package-host`, release packaging inputs, and any other file actually shipped at runtime. Enforce one version bump and dated CHANGELOG entry per released change set. Keep canonical Claude frontmatter and README checks. Compare version to an explicit merge base for PRs. Retain tag/version check for releases. Generated native descriptors and archives must reproduce from the same tree.
- **Validation.** Use `tools/ci-local` as the shared entry point. Check archive inventory and file modes, parse native descriptors, validate relative references, role allowlists and explicit-only entries, and test Windows paths, quotes, spaces, empty settings, non-default homes, multi-root projects, remote contexts, absent interpreters and disabled hooks. Python 3.9 has no stdlib TOML reader. Generate a small fixed TOML subset and validate with a newer CI interpreter's `tomllib` plus a real Codex load. Run each host's documented validator if the pinned release exposes one. `claude plugin validate .` exists. Codex 0.167.0 plugin help exposes list/add/remove/marketplace, with no dedicated validate command. No standalone Copilot CLI or VS Code validator was established here. Pin evidence before adding such commands. An isolated real install/discovery check covers what a schema cannot.
- **Desktop acceptance.** Test the Codex extension and local VS Code Copilot separately, including a custom profile or relocated user-data directory. Check the displayed skill, explicit invocation, rerun/undo, no automatic skill selection, hook delivery, package removal and coexistence with Claude. Use an OS-native Windows run for packaging and a no-Bash run to prove the core Python path or give a precise prerequisite. Run noninteractive CI without account credentials. Run authenticated acceptance on a consenting user's disposable workspace and retain only a short, sanitized result. A skipped native smoke leaves that host unverified.

## Decisions needed

1. **What counts as supported?** Recommend the three local packages and two Codex UI smoke tests. Ship the core workflow even where token measurement, hooks or delegation are partial. Publish versions and limitations per host. Keep cloud repo guidance as a documented use case outside the installation promise.
2. **Distribution and default activation.** Recommend generated release ZIPs/local marketplaces, with explicit-only commands and optional non-Claude hooks enabled individually. This avoids keeping rendered copies in source control and gives administrators a reproducible offline install. Defer a public Git marketplace mirror until direct source installs are required.
3. **State ownership and unattended access.** Recommend a neutral, overrideable state root for the ports, keep the existing project ledger, and make reuse of a Claude state directory explicit. Ship interactive work and measured, zero-token audits first. Defer a new model-backed scheduler, machine-wide changes and any expansion of existing allowlists.
4. **Accounting claims.** Recommend partial figures with named sources and unavailable reasons. Add a Copilot CLI token total only for attributable persisted fields. Defer a paginated Codex reader and editor/cloud ingestion until a supported read interface, coverage model and fixtures exist. Never enable telemetry or cloud sync to obtain a result.
